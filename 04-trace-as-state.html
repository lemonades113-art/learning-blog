Trace as State：这篇其实只有七层意思

先给总判断：这篇研究的不是“怎么把 context window 再做大”，而是 causal Transformer 在长上下文里有一个顺序问题：真正决定怎么理解前文的 task state，往往在后面才被发现。作者先让模型跑一遍，用 reasoning trace 把这个后发现的 state 显式化，再在第二遍把 trace 放到整个长 context 前面，让模型带着已经发现的状态重新阅读。

原文：Trace as State: Reasoning Traces as Conditional States for Long-Context Transformers（arXiv:2609.02702）。作者 Xu Zou、Jie Tang，2026 年 9 月 2 日提交。

第一层：它先指出“上下文够长”不等于“模型读对了”

我们通常把 long-context failure 理解成两种问题：要么 context window 不够长，要么模型把前面的东西忘了。但这篇论文抓的是第三种结构性失败：信息虽然全在 context 里，模型第一次读到前半段时，却还不知道后面才会出现的真正任务状态。因果 Transformer 从左到右处理，后面才出现的信息可以影响后续生成，却不能回头改写同一遍前面已经形成的表示。比如一开始给你几十万条图的边，最后才告诉你“找节点 A 的所有 parent”，模型读前面那些边时并不知道哪些边重要；等它最后知道 A 是谁，前面的内容已经看过一次了。所以论文真正重新归因的是：长上下文推理失败不一定是“没记住”，也可能是状态发现得太晚，导致前文是在错误条件下被处理的。

第二层：为什么“把条件放前面”不只是 Prompt Engineering？因为作者先做了一个理论抽象

作者把问题形式化成 conditional state update：一个 causal processor 从左到右维护状态 s，不断吸收上下文 c_i。如果一开始就知道条件 z，例如“目标是 A”，它只需要维护与 A 相关的状态；但如果 z 最后才出现，为了保证最后能回答任意可能的 z，最坏情况下它可能需要提前保存对许多可能条件都足够的信息。论文证明，在构造的最坏情形下，condition-first 可以比 condition-last 需要指数级更少的 memory。这个理论的作用是说明“顺序”可能不是一个小的 prompting 偏好，而是 causal processing 的结构问题。不过边界也必须说清：这个 theorem 讲的是抽象的 causal state-update processor 的 worst case，不等于已经证明真实 LLM 的每一个 long-context task 都有指数级差距；真实模型到底有没有这个现象，还要看后面的实验。

第三层：Trace as State 的方法其实极简单——第一遍发现状态，第二遍带着状态重读

具体方法就是“Read → Compute → Feedback → Reread”。第一遍，模型照常读原始长 context 和 question，并生成若干 reasoning traces；这些 trace 往往已经包含第一遍推理才发现的实体、目标、候选、搜索边界和局部结论。第二步，把这些 traces 序列化成一个文本块 T。第三步开始 fresh pass，但这次输入顺序改成 [Trace T → Long Context → Question]。作者把 T 叫 task-state 的 textual proxy，而不是模型真实 hidden state：它只是在语言层面携带了第一遍才获得的状态信息。整个过程不改参数、不做训练、不改 Transformer 架构，本质上是一种 inference-time scaling：同一个模型多跑一遍，但第二遍不是简单重复，而是带着“第一遍已经知道的事”重新处理原始长上下文。

第四层：最漂亮的地方不是涨分，而是 matched control 把“为什么涨”钉住了

如果只比较第一遍和第二遍，涨分可以有很多解释：多算了一遍、多看了 trace、token 更多、甚至只是随机性。因此作者设计了 Trace Append 这个 matched control。Trace as State 用 [Trace → Context → Question]，Trace Append 用 [Context → Trace → Question]；两边用同一批 trace、同一份 context、同一个问题，真正改变的只有trace 在长 context 前面还是后面。如果提升只是因为“有 trace”，Append 应该也差不多；如果“先知道 state，再读 context”才是关键，Trace as State 就应该明显更强。论文报告它在三模型、三数据集的 27 个 model-task-metric 组合中，有 26 个优于 Trace Append。这个对照的价值非常高，因为它不是问“我的方法有没有用”，而是在问“涨分是不是来自我声称的那个机制”。

第五层：实验结果很强，但 claim 只能到“tested settings 下 placement 很重要”

最醒目的数字来自 GraphWalks Parents：DeepSeek V4 Pro Preview 的 exact match 从 initial pass 的 29.2%，到 Trace Append 的 43.0%，再到 Trace as State 的 81.8%；GLM-5.2 则从 66.4% 和 83.2% 提到 100.0%。这说明在这些 tested long-context tasks 里，把第一遍得到的 trace 放到上下文前面，效果可以远高于只是把 trace 附在后面。但这里不能把“26/27 更好”直接升级成“理论机制被完全证明”或“所有 long-context 任务都适用”。实验能支持的是：在作者测试的三类数据集和三个模型上，trace-first placement 的趋势非常一致，而且部分任务提升巨大；它不能证明这就是模型内部唯一的因果机制，也不能证明动态 Agent、多轮工具环境会自然得到同样结果。

第六层：标题叫 Trace as State，但 reasoning trace 不能偷换成“模型真实内部状态”

这是最容易被二手文章说过头的地方。论文的谨慎说法是 reasoning trace 是 textual proxy for task state：它可能把“目标是谁、已经排除了什么、当前在搜索哪里”这些状态显式记录出来，因此对第二遍推理有用；但它可能错误、遗漏、冗余，也绝不等于 Transformer 的 hidden state。实验只说明“把这种 textual proxy 放在 context 前面对重新阅读有帮助”，并没有证明 CoT 就是模型真实 state，也没有证明 theorem 里的 memory separation 就是所有提升的唯一原因。按论文调研的 claim-level 规则，这里必须把“proxy”“task state”“internal state”三者严格分开。

第七层：对 Agent / UserSim 真正值得迁移的是一个机制假设——state 是附加摘要，还是重读历史的条件？

这篇论文不能直接拿来证明 UserSim 的 Profile/State 应该怎么设计，因为它测的是静态 long-context reasoning，没有真实用户、工具状态变化、intervention，也没有 Agent action 改变环境。所以我会把它放在 MECHANISM_REFERENCE，不是 DIRECT_REUSE。但它能逼出一个对我们非常具体的问题：如果 Profile / State / Goal 是读完历史以后才推断出来的，那么把它简单附在历史末尾，和让模型带着这个 state 重新解释历史，可能不是同一件事。一个很直接的实验就是比较 [History → Inferred State → Current Stimulus] 和 [Inferred State → History → Current Stimulus]，其余条件完全相同；如果后者稳定更强，就说明 state 不只是“最后附加的一段摘要”，而可能需要成为重读历史的前置条件。这个项目迁移是根据论文机制推出来的研究假设，不是论文已经替我们证明的结论。

一句话复述

Trace as State 不是在扩大 context，而是在修“状态发现得太晚”这个顺序问题：先跑一遍把 task state 从 reasoning trace 里显式化，再把它放到长 context 前面重新读；matched control 说明关键不只是“有 trace”，而是“state 在 reread 之前”。它对我们最值得复用的不是某个 prompting 模板，而是一个可验证的机制假设：后推断出来的 state，到底应该附在历史后面，还是应该作为重新解释历史的条件。

原文链接：https://arxiv.org/abs/2609.02702
