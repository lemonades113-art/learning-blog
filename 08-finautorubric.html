FinAutoRubric：真正重要的不是“自动写 Rubric”，而是把 Rubric 变成一条可编译、可复算、可审计的生产链

先给总判断：这篇论文和我们现在做金融 Agent Rubric 的关系非常直接。它真正解决的不是“让另一个 LLM 帮忙写几条评分项”，而是把原来混在一张评分表里的四种东西彻底拆开：专家长期稳定的评价原则、某类任务反复成立的通用检查机制、某一道题自己的实体/期间/假设/截止日，以及这一题最终可核验的 expected value 与容差。拆开之后，Rubric 就不再是一份手工答案表，而像一个编译系统：原则是源规则，Task Bank 是可复用的中间表示，具体题目提供 context binding，最后才编译成这一题的可执行评分表。对我们最关键的启发是：Rubric 的权威来源应该在“机制和原则”，Gold/Expected Value 负责把这些机制在具体题目上落地，而不是反过来用 Gold 临时发明评分标准。

论文：FinAutoRubric: Expert-Guided Automatic Rubric Generation for Evaluating Financial Research Agents（arXiv:2609.35744，2026-09-28）。作者来自 LinqAlpha、UNIST、MassMutual、AllianceBernstein、Wolfe Research、Google、BlackRock、J.P. Morgan Chase、State Street、Fidelity、Blackstone、University of Florida 等机构。

第一层：它先改了问题定义——金融 Rubric 最大的问题不是“人工写得慢”，而是“固定答案天然会过期”

如果只是把这篇理解成“人工写评分标准太贵，所以让模型自动写”，其实还没有抓到根。金融任务和普通知识问答最大的差别，是同一个分析问题在不同时间、不同机构、不同数据权限下，正确答案本来就会变：新财报出来以后 LTM 数字会滚动，历史口径可能重述，某个机构允许使用内部数据库而另一个只能使用公开披露，materiality、风险容忍度和证据标准也可能不同。因此一张人工手写、永久冻结的 Rubric 同时绑死了任务机制、具体公司、具体期间、当时可见的信息集和机构标准，只要其中任何一个变了，就得重新人工维护。FinAutoRubric 真正要做的是把这些变化速度不同的对象解耦：长期稳定的专家原则不应该跟着每季度财报重写，真正需要动态刷新的只是具体题目里的 context 和 expected values。于是“自动生成 Rubric”只是表面，底层其实是在解决 Rubric 的版本化和可迁移问题。

第二层：它最核心的结构是四层分离——Principle → Task Bank → Context → Rubric Instance

论文的架构可以压成四层。最上面是专家写的 Principle Library，定义什么叫范围忠实、证据可靠、实体和期间对齐、时间边界完整、计算可复核、因果有依据、结论有决策价值；第二层是 Task Bank，把大量具体题目先去掉公司名、年份和具体数字，抽成“这个任务到底在做什么”，再为同一类任务沉淀通用 criteria，最终形成 200 个 task、1,224 条 task-level criteria；第三层才是某一道具体 query 的 context，把实体、期间、指标、假设、deliverable、输出约束、convention topic、population 等绑定回来；第四层才生成这一道题真正拿来打分的 Rubric，把抽象 criteria 绑定到这一题的具体 expected value、证据、容差和分值。这个结构最值得我们学，因为它说明一个成熟 Rubric 系统不应该只有 `rubric.json`，而应该至少能追溯到“哪条专家原则 → 哪类任务机制 → 这道题哪段要求 → 哪个具体评分 target”。

第三层：为什么一定要“先定题，再检索”——因为证据不能反过来污染任务定义

FinAutoRubric 有一个看起来很细、其实非常关键的设计：Stage 2 做 contextualization 时，系统先只看 query，把任务签名和具体 bindings 锁定，在这一步完成之前不允许外部检索结果进来。原因是如果模型一边搜索一边决定“这题到底要考什么”，它很容易被自己先搜到的材料牵着走：哪个数字容易找就把哪个当重点，某个定义搜不到就悄悄缩窄题目，甚至把数据库里现成的口径反向解释成用户原本的意图。论文因此要求任务签名保持 value-free，具体 binding 尽量从原 query verbatim 拷贝，并且先写死 information cutoff；之后搜索只能解决“这个已定义义务的真值是什么”，不能再改“义务本身是什么”。这实际上是在给 Rubric 建一个防数据泄漏的因果顺序：先定义考试范围，再找答案；不能因为答案好找才决定考试范围。

第四层：金融 Rubric 不能只是“覆盖哪些维度”，它必须落到 Expected Value、Tolerance 和 Provenance

这篇对通用自动 Rubric 方法最直接的批评，是很多方法可以写出非常全面的 checklist，却没有给裁判一个可核对的真值。论文里 Qworld 在“如果不要求具体值，只看维度有没有覆盖”这一项可以做到非常高的覆盖率，但一旦要求 criteria 同时写明 expert rubric 的 expected value，覆盖率就明显掉下来，而且最终模型排序一致性也不理想。金融里这件事尤其致命：说“需要计算 leverage ratio”并没有把一个答案变成可判分对象，Rubric 必须继续落到用哪个期间的 debt、哪个 EBITDA 定义、怎样处理调整项、最后 accepted value 是多少、允许多大 tolerance、这些输入来自哪里。于是 Rubric 的最小可执行单元不再是自然语言要求，而是更接近criterion + target + expected value + tolerance + evidence/calculation provenance。没有这一层，Rubric 看起来专业，实际上只是写作提纲。

第五层：它又往前走了一步——不是直接从问题生成评分项，而是先生成“任务契约”

Stage 3 里 writer 不只是写评分句子，而要提交 evidence record、candidate answer 和 typed task contract。这个 contract 先把 query 中每一个 obligation 绑定到真正决定它是否完成的 targets，再区分 core outcome、required justification 和 support。这个设计解决的是一个长期很难处理的问题：金融长任务既不能只看最终数字，也不能把每个中间步骤都平均打分。只看 final outcome，一处计算错误会把前面大量正确工作全部抹掉；但如果把所有中间步骤都当成同等重要，又会出现“核心结论没交付，靠过程分也拿一半”的怪现象。FinAutoRubric 的做法是结果优先、过程可追责：最终 outcome 必须拿到过半分值，但重要的输入、公式和中间计算可以单独设行，让错误定位和部分得分都成立。这一层对我们特别重要，因为 Rubric 的粒度不应该由“能拆多少步骤”决定，而应该由“哪些 load-bearing target 决定任务真的做成”来决定。

第六层：真正可靠的地方不是“用了两个模型”，而是把语义判断和硬约束分给了不同控制面

论文把专家 guidance 同时写成两种东西：一部分作为 `G_prompt` 进入模型，让 Agent 理解什么叫合格的金融研究；另一部分作为 `G_code` 写进 orchestrator，直接拒绝违反硬规则的产物。这个区分非常重要，因为“points 必须加起来等于 100”“不能使用 cutoff 之后的来源”“每个 target 只能被打一次分”“结构修改必须有 material finding”“最终 outcome 分值必须过半”这类条件，本质上不是需要大模型判断的开放语义问题，而是应该由程序 deterministic enforce 的 invariant。模型适合做检索、会计口径判断、分析 reasoning 和 ambiguous convention 的解释；代码适合做预算、schema、唯一性、时间边界和 gate。换句话说，不要让 LLM 同时当分析师、规则制定者和规则执法者。专家定义规则，模型完成高语义工作，代码负责卡死不能被协商的边界，这才是它真正的可靠性来源。

第七层：异构 Writer–Reviewer 的意义不是“互相看看”，而是要求独立复算同一个真值

Writer 用带搜索和 Python 的环境查来源、算 expected values；Reviewer 来自另一模型家族和另一套 harness，在隔离环境里重新打开来源、检查 cutoff、重新推导计算、核对 target 类型和 score role，并把问题打回 Writer；局部每条过关以后，全局 reviewer 再看整张 Rubric 的分值结构、是否 double scoring、是否 outcome priority，重大结构修改还要由 fresh session 再确认。这里真正应该学的不是“Claude 审 GPT”这个表面设定，而是reviewer 必须拥有独立证据路径，能够重新计算，而不是阅读 writer 的解释后说看起来合理。如果 Reviewer 只是语言润色，Writer 的事实错误仍然会原封不动地传播；只有 source reopening、re-derivation 和 fresh-session confirmation 才真正构成独立验证。失败超过次数以后系统直接 HOLD 并升级人工，也说明它的目标不是保证自动化率，而是保证没有验证过的 Rubric 不会被悄悄发布。

第八层：这篇最有价值的实验不是“模型分数”，而是它开始评测 Rubric 本身到底是不是一个好测量工具

FinAutoRubric 没有只展示几张漂亮 Rubric，而是问了四个更硬的问题：它给一批 agent responses 排出来的顺序和专家 Rubric 是否一致，用 Kendall’s τb；它给出的绝对分数与专家评分差多少，用 MAE；它有多少 criteria 真正给出了专家所要求的具体 expected values，用 value coverage；最后，人类分析师盲审时到底愿不愿意拿这张 Rubric 来工作，以及 Rubric 排序是否和人工逐对比较一致。结果里，BigFinanceBench 上 τb 为 0.616、MAE 为 19.0pp、value coverage 为 60.8%；ProfBench Finance 上与人工 grading 的 pairwise accuracy 为 84.6%；45 道题的盲审中总体 79% 的判决偏向 FinAutoRubric。更重要的是 ablation：去掉 contextualization，τb 掉到 0.485；去掉 review loops，coverage 从 60.8% 掉到 41.9%。这说明 Rubric 质量不能靠“专家看起来觉得写得完整”来验收，必须看它作为测量工具是否真的改变正确响应与错误响应的排序，是否能抓住关键 expected value，以及其失败能不能被人类复核。

第九层：它没有解决“Rubric 真理”问题——它把工程可靠性推进了很多，但 construct validity 仍然要单独证明

论文自己把边界讲得很清楚：自动 review 能保证来源 grounding、内部 consistency 和选定 convention 下的计算成立，但不能证明一个有歧义的 query 被解释成了原作者真正想表达的意思；expert point-scale calibration 和同一 task 下不同 query 的 consistency 仍然没有被直接测量；整套 writer/reviewer 长程循环每题给到数千秒级预算，明显比单次生成更贵；论文也没有研究把这些自动 Rubric 直接拿去当训练 reward 会不会出问题。因此这篇不是在说“Rubric 已经可以完全无人化”，而是在告诉我们应该怎样把 Rubric 从一份静态文档升级成一个有 provenance、有独立复算、有 acceptance gate、有 human escalation 的工程对象。真正的 measurement validity——题到底在测什么、某个 failure 能不能归因到预期能力、难度机制是不是被 Rubric 抓住——仍然需要我们自己做。

对我们现在 Rubric 设计的第一条直接影响：把一张 Rubric 拆成四层 SSOT，而不是继续把所有东西写进一个 JSON

我会把现在的 Rubric Factory 明确拆成 Principle Library → Task/Mechanism Schema → Context Binding → Rubric Instance。Principle Library 放长期稳定的金融评价原则，例如 scope fidelity、entity/period alignment、temporal integrity、numerical reconciliation；Task/Mechanism Schema 放某一类任务反复成立的 load-bearing checks，例如 FCFF 估值必须有 forecast driver、WACC、terminal treatment 和 bridge，审计任务必须有 population、sample/evidence、exception treatment；Context Binding 才绑定这道题的公司、期间、事件、会计口径和 cutoff；Rubric Instance 最后再绑定 concrete expected values、tolerance、evidence 与 points。这样我们以后改一道题的数字，不会误伤全局机制；反过来发现某类任务的评分机制有问题，也能改 task schema 后系统性重编，而不是逐题手修。

第二条直接影响：这篇实际上把“Golden 到底是干什么的”讲得非常清楚

Rubric 的评价原则和任务机制必须先于 Golden。先由专家原则和 Task Schema 决定“什么东西值得打分、为什么它是 load-bearing”，再由具体 context 下的 evidence research / oracle calculation 产出这一题的 expected value，Golden 或 reference state 的作用是把这些 criterion 在具体实例上绑定成可验算真值，并验证我们的规则实现有没有算对。也就是说，Golden 很重要，但它不应该反过来定义评分哲学。最危险的做法是“先看 Golden 里有什么字段，再给这些字段分数”，因为这样很容易把偶然实现细节当成能力目标；正确方向是“先定义任务必须完成的机制义务，再让 Golden 给这些义务提供具体实例真值”。这和我们一直想区分的 Rule/Oracle/Golden 三层关系是完全一致的。

第三条直接影响：每一条 Rubric item 都应该带完整 provenance，能够一路追到“为什么有这一分”

以后一个 rubric item 最好不要只有 `criterion / points / expected`，而应至少可以追到：source principle → task/mechanism criterion → query obligation / 原题 span → context bindings → evidence or calculation artifact → expected value / tolerance → score role → reviewer re-derivation → acceptance gate。这条 lineage 非常重要，因为我们现在真正想防的不是格式错误，而是“看起来合理、其实没有机制来源”的伪难度与伪评分项。只要 provenance 完整，后面做 difficulty audit 时就能直接问：这个所谓 L4/L5 难点到底落在哪条 obligation 上？这条 obligation 的错误会触发哪一个 rubric item？这个 item 的真值是谁算出来、谁独立复算、哪个 mutant 能打穿它？这样 Rubric 才真正成为难度机制的 measurement hook，而不是任务完成以后补写的一张表。

第四条直接影响：分值设计要代码化，但不能机械照抄“所有 obligation 初始均分”

FinAutoRubric 先把每个 query obligation 平均分配 100 分并冻结，目的是防止 Writer 因为先搜到某些熟悉信息就擅自提高其权重，之后 global loop 才在有 material finding 时调整，而且硬性要求 outcome rows 占过半。我们应该学的是“权重不能由生成模型自由发挥，必须有显式政策和程序门禁”，不一定要原样照抄平均分。我们的金融复杂任务很多难度本来就来自不对称的 load-bearing mechanism：例如一处 rule-version 选错可能让后面整个 valuation 全错，这种机制应该在 Task Contract 阶段就有明确权重逻辑。因此更合适的做法是由 obligation / mechanism schema 先声明 score-role 和 load-bearing class，再由代码按固定政策分配，任何跨义务改权都必须留下 material reason 和 fresh validation，而不是让 Judge 看心情改分。

第五条直接影响：Rubric 自己必须有 Benchmark，不能只 Benchmark Solver

我们后面验收 Rubric Factory 时，至少应该把论文里的四类指标拿进来：Response Ranking Agreement 看和专家/可信 Rubric 对同一批答案的排序一致性；Score MAE 看绝对分值偏移；Expected-Value Coverage 看有多少关键 quantitative/factual criteria 真正落到了可核验值；Human Pairwise / Blind Preference 看专家实际愿不愿用，以及它能不能区分人工认为明显更好的 response。然后再加我们比论文更需要的一层：Mutant Sensitivity。给 Golden 系统性注入 wrong formula、wrong period、wrong entity、wrong rule version、wrong history、rounding、cross-round inconsistency 等错误，如果这些 load-bearing mutant 没有稳定打中预期 gate，就说明 Rubric 看起来完整但测量是漏的。这样 Rubric 的验收从“写得像不像专家”变成“能不能稳定杀死我们真正关心的错误机制”。

第六条直接影响：Reviewer 的工作对象应该从“Rubric 文案”升级为“Expected Value 与证据链的独立复算”

我们现有的 scorer/oracle/rubric review 如果只是让第二个模型看一遍 JSON，很容易形成 correlated error；FinAutoRubric 更强的地方是 reviewer 必须重新打开 source、重新跑 calculation、检查 cutoff 和 convention，再判断 writer 的 target 是否成立。因此对我们来说，真正高风险的 quantitative rubric item，Reviewer 应拿到最小必要原始材料 + 规则定义，自己重新导出 expected state，而不是直接读 writer 的中间推理后做“审稿”。甚至可以把 reviewer 的 independent result 与 writer 的 result 做 deterministic diff，只有 disagreement 被解释清楚才进入 canonical。这样双模型的价值才是独立测量，不只是多一次语言判断。

第七条直接影响：它强化的是“Rubric 有效性”，不是直接告诉我们“题怎么变难”

这点必须分清。FinAutoRubric 并没有定义 L1–L5，也没有证明怎样增加任务难度；它解决的是当一道题已经包含某个复杂机制时，我们怎样确保 Rubric 真的测到了这个机制，而且真值和证据可靠。所以它对 difficulty 工作的作用不是替代难度定义，而是补上“难度机制 → measurement hook”的中间桥。我们仍然需要先定义 mechanism provenance：某个任务为什么难、必须维护什么状态、跨哪几个 dependency、错在哪里会导致什么业务后果；然后用这篇的方法把这些机制编译成可追溯 criteria、具体 expected value 和 independent validation。换句话说，Difficulty 决定“我要考什么”，FinAutoRubric 这套方法决定“我怎么保证真的考到了”。两条线合起来以后，我们的 Rubric 才既不是空 checklist，也不是围着 Golden 临时拼出来的评分表。

最后压成一句话

FinAutoRubric 最值得我们拿走的，不是“双模型写评分表”，而是一条 Rubric Compiler：专家原则决定长期不变的评价逻辑，Task/Mechanism Schema 把原则变成可复用检查，Context 把具体题目的实体和时间绑定进去，Writer 用真实证据生成 expected value，独立 Reviewer 重新复算，代码 Gate 冻结不可协商的规则，最后再用 response ranking、value coverage、human judgment 和 mutant tests 去验证这张 Rubric 本身是不是一个有效测量工具。如果我们按这个方向改，Rubric 就会从“任务生成后的附属文件”变成整个 Finance Factory 里真正独立、可审计、可以持续迭代的一条生产线。
