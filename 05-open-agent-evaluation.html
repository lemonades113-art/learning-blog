开放任务评测真正难在哪：先把“人怎么判”搞清楚，再训练 LLM Judge

先给总判断：这篇真正讲的不是“怎么写一个更好的 Judge Prompt”，而是开放任务里首先要把评测本身做成一套可信的测量系统。编程任务有测试用例，办公 Agent 很多时候没有唯一答案，所以如果 Rubric、人类标准、边界案例和 review 机制都没有钉死，后面任何“模型变好了”“新版本回归了”“某个改动有效”都可能只是尺子漂了。

第一层：办公 Agent 最先缺的不是更多能力，而是一把稳定的尺子

编程任务相对容易评，因为很多结果能被 compiler、unit test 或 execution state 直接验证；办公任务则不一样，同一个交付物可能同时涉及完整性、专业性、表达、格式、事实正确性和业务可用性，而且这些目标之间还会互相权衡。所以开放任务真正困难的地方不是“Judge 会不会打分”，而是到底什么叫好，以及这套标准能不能被不同评审稳定执行。一旦这一步没做好，Agent 分数变化就无法归因：可能是模型真变强了，也可能只是 Judge 口径变了。换句话说，Evaluation 不是最后一道评分工序，而是整个 Agent 迭代闭环的测量基础设施。

第二层：Judge-Human 之前必须先做 Human-Human，因为人自己不一致时，模型不一致未必是模型错

最容易犯的错误是直接拿 LLM Judge 和一个人工标签算一致率，然后把差异都算在 Judge 头上。更合理的顺序是先让多个人独立盲标同一批样本，先测 Human-Human agreement。因为如果人之间都在使用不同标准、不同信息来源或不同业务目标，那“Judge 和某个人不一致”本身并不能说明 Judge 有问题，反而可能说明任务定义还没冻结。Human-Human 的价值因此不是给 Judge 设一个简单上限，而是做 measurement diagnosis：到底是 rubric 模糊、输入信息不一致、业务代价理解不同，还是样本本身真的存在不可消除的不确定性。只有这些分歧原因被拆开以后，才有资格谈 Judge-Human。

第三层：Raw Agreement 只是第一步，Kappa 能扣掉偶然一致，但也不能被当成唯一真理

如果 90% 的样本本来就是 Accept，一个 Judge 全部判 Accept 也可能拿到 90% raw accuracy，所以单看 agreement 很容易被类别分布骗。Cohen’s Kappa 的作用是扣掉根据两边边际分布“本来就可能碰巧一致”的那一部分；如果评分是 1–5 分或差/中/好这类有序等级，则 Weighted Kappa 更合适。但这里也要继续封住追问：Kappa 自己也会受 prevalence 和 marginal distribution 影响，类别极不均衡时可能出现 raw agreement 很高、Kappa 却异常低的情况。所以真正稳妥的评估不该单押一个数，而应该同时看 raw agreement、confusion matrix、Kappa/Weighted Kappa，以及 boundary slice 上具体错在哪里；如果 prevalence 特别极端，还可以考虑 Gwet’s AC1/AC2 这类更稳的补充指标。关键不是追求一个漂亮系数，而是知道“不一致到底发生在哪种样本上”。

第四层：HH-main 和 HH-boundary 不是两份重复数据，而是在分别测“整体可靠性”和“最危险边界”

按真实业务分布随机抽样得到的 HH-main，用来估计整体环境下人和人有多一致，它回答的是“这把尺子日常使用时大体稳不稳”；而 HH-boundary 要主动过采样高冲突、低频但高代价、最容易误判的案例，它回答的是“真正会把系统搞坏的边界在哪里”。这两个集合如果混在一起，既估不准整体分布，又找不清关键 failure mode。更好的理解是：main set 是 calibration baseline，boundary set 是 stress test。前者告诉你平均可靠性，后者逼你真正定义 decision boundary，二者一起才构成一个可以持续维护的 evaluator benchmark。

第五层：Anchor 比 Few-shot 更重要，因为真正需要教给 Judge 的是“最小决定性差异”

开放任务里最危险的错误往往不是完全不懂，而是两个案例看起来几乎一样，但业务结论必须相反。普通 few-shot 只是告诉模型“这个例子判 Accept”，却未必告诉它为什么；Anchor 要更进一步，明确它校准哪个维度、在哪些条件下适用、正例需要满足什么，同时必须给一个 Dangerous Neighbor——一个非常像正例但结论相反的最近邻。最关键的是再指出 Minimal Decisive Difference：两个案例其余条件几乎不变时，最少改哪一件事，业务判断就必须翻转。这样 Judge 学到的才不是表面模式，而是 decision boundary。对 evaluator 来说，这种成对边界案例往往比单纯继续堆 rubric 条目更有价值。

第六层：好的 Judge 不应该被迫每题都判，它还要学会什么时候触发 review_required

如果某些样本的分歧来自真实不确定性，而不是 rubric 没写清楚，那么强迫 Judge 在所有样本上都输出 Accept/Reject 会制造一种假的确定性。更合理的系统是让 Judge 有第三种 action：review_required。这样评测问题就从“分类准不准”升级成 selective prediction：在可接受风险水平下，Judge 能自动处理多少样本；被送去人工复核的 slice 是否真的集中在高不确定性和高代价边界上；随着 Anchor 和 Rubric 迭代，自动覆盖率能否提高而错误率不升。换句话说，成熟 Judge 的目标不是 100% 自动化，而是知道什么时候自己有资格自动做决定。

第七层：最终 Judge 应该被当成业务决策系统，而不是一个 Prompt

把前六层串起来，会发现 LLM Judge 的建设顺序其实是：先定义任务和成功标准，再做 Human-Human 校准，冻结 Rubric 和 Anchor，接着做 Judge-Human，一直分析 boundary 和高代价错误，最后定义哪些样本可以自动 Judge、哪些必须 review；上线后还要持续把新分歧回流到 boundary set 和 Anchor。这样 Judge 才会形成“学习—验证—诊断—改进—沉淀”的闭环。至于“多目标 Pareto 进化”是不是最优实现路线，在文章当前截断位置还不能直接下定论；现在能确认的是，Judge 已经不能被理解成一个静态 prompt，而应该被理解成一个有数据、标准、边界、验证和升级门槛的多层业务决策系统。

对我们最直接的项目含义

如果把这套思路迁到 Benchmark / Rubric / Scorer 里，正确顺序应该是：先 Human-Human 校准 → 再冻结 Rubric / Anchor → 再测 Judge-Human → 再单独看 boundary / high-cost failure → 最后决定自动 Judge 和 review gate。这会补上一个很容易被忽略的环节：不仅要证明 scorer 能区分 golden 和 mutant，还要证明这把尺子的业务判断本身由稳定的人类标准支持。否则 scorer 再稳定，也可能只是稳定地执行一套没人真正统一过的标准。

一句话复述

开放 Agent 评测真正难的不是“怎么让 LLM 打分”，而是先把人类判断做成一套稳定、可解释、可复核的标准，再让 Judge 学这条 decision boundary；Human-Human 用来诊断尺子本身，Anchor 用来钉住最危险边界，review_required 用来处理真实不确定性，最后 Judge 才能从一个 Prompt 变成可信的业务决策系统。

默认写法：原问题 → 测量矛盾 → 具体方法 → 边界案例 → 指标限制 → claim 边界 → 项目迁移；所有容易被追问的地方提前封口。
