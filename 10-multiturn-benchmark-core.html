多轮 Benchmark 真正该测什么：从“需求分片”到隐藏意图、记忆和跨轮 Rubric

先给总判断：这组工作非常有帮助，而且它们比泛泛的“multi-turn benchmark”更接近真正的问题。最重要的是，它们并不是都在测同一件事：LLMs Get Lost 证明“同一个任务只要把信息分轮给，模型就会出现新的不可靠性”；π-Bench 把“用户没说全的 hidden intent”变成独立评分对象；MemoryAgentBench 把跨轮记忆拆成检索、在线学习、长程整合和冲突/遗忘；而更新的 MemoryArena 再证明“记得住”不等于“能在后面的真实任务里用出来”。四篇拼起来以后，多轮不再是“轮数多”，而是四种因果机制：信息在时间上分开、需求需要主动恢复、旧状态必须被正确保留/更新、过去经验必须真正改变后续行动。

原文：LLMs Get Lost In Multi-Turn Conversation · π-Bench · MemoryAgentBench · MemoryArena

第一层：LLMs Get Lost 最重要的不是“多轮会掉分”，而是它用 matched control 证明了“多轮本身”是一条独立能力轴

这篇最漂亮的地方是构造方法，而不是 39% 这个数字。作者拿原本完整、可单轮解决的任务，把同一条完整 instruction 拆成若干信息 shard，再让模拟用户逐轮释放；为了排除“只是改写文本导致信息损失”，又设计 FULL、SHARDED、CONCAT 和 RECAP 等控制条件：FULL 是完整原题一次给完，CONCAT 是把所有 shard 重新拼成一次性完整输入，SHARDED 才是真正逐轮披露，RECAP 则在多轮末尾再把全部要求重述一次。结果模型真正的问题不是突然“不会做这个任务”，而是信息分轮后会更容易在早期缺信息时自行假设、提前给完整方案，然后后续新信息来了也不愿推翻旧路径，最终表现下降主要来自 unreliability 而不是 aptitude 消失。对多轮 Benchmark 来说，这篇给出的最关键方法论是：不要重新造一套更难的题来证明多轮难，而应该保持底层任务和最终真值不变，只改变 information protocol；单轮和多轮的差值，才更有资格叫 multi-turn tax。

第二层：这篇对我们最直接的用法，是给每道多轮题做“单轮信息完整版”对照，否则永远说不清到底是金融题难还是多轮难

如果一道金融任务 R1 给初始数据、R2 给修订、R3 给外部事件、R4 要最终报告，只跑这一个版本，模型低分时无法归因：可能它不会估值，也可能它跨轮状态没维护好。正确借法就是把同一个 World、同一个 Golden、同一个最终 Verifier复制成 matched arms：Arm A 在 t=0 一次给全部合法信息，Arm B 按固定轮次释放，Arm C 再把必要信息藏到 UserSim 交互里。这样如果 A 很高、B 明显掉，说明 stateful multi-turn execution 有额外负担；如果 B 高、C 再掉，才说明 hidden-intent clarification / user interaction 又是一条额外能力。这比“我们的题有五轮，所以是多轮 Benchmark”硬得多，因为它直接回答构念效度：究竟是哪一种时间结构让能力掉下来的。

第三层：π-Bench 更接近老师追问的另一半——最终任务完成不等于 Agent 真正解决了用户没说出来的需求

π-Bench 的核心设计是 persistent episode：每个 persona 有一条共享 workspace 的 20-session 长程工作流，文件、偏好、前一次交付和任务依赖可以跨 session 保留；每个 session 的 initial request 故意只说显式 deliverable，不把全部 preference、constraint、dependency 一次讲清。Benchmark 私下维护 hidden intents，这些信息可能来自 persona/profile、历史 session、workspace 文件、app state、tool result 或跨任务依赖；Agent 可以自己从上下文推出来，也可以在真正需要时问一个 focused clarification。于是它把评分拆成两个互不替代的轴：COMP 看最终 trajectory / artifact 有没有满足任务 checklist，PROC 看 hidden intent 是不是由 Agent 自己推断出来或通过针对性澄清主动 elicitation，而不是等用户直接喂答案。这个拆法特别重要，因为两个 Agent 最终都能完成任务，但一个可能一路让用户反复纠正，另一个能自己恢复隐藏约束；普通 final score 看不出差异，PROC 才把“用户负担”变成可测对象。

第四层：π-Bench 真正值得我们抄的不是 persona 数量，而是“private intent ledger + outcome rubric”双轨评分

把它迁到 General Work / Finance，不应该照抄 researcher、financier 五类人设，而应该照抄它的权威结构：Benchmark private side 先保存 required intents / constraints，以及这些 intent 的来源和何时有资格被发现；运行时 Agent 只能看到当时合法可见的 history、workspace、tools 和用户消息；结束以后一套 Outcome Rubric 检查任务到底做没做对，另一套 Interaction Rubric 看关键 intent 是被 Agent 主动恢复、主动问出，还是用户不得不纠正后才出现。这样“澄清能力”就不再用裸轮数表示，而可以问：必需 intent 覆盖了多少、多少是 Agent-driven、有没有在未知条件下 premature action、用户补了几次、纠正以后多久恢复。这个结构和老师问“你怎么体现这是多轮而不是普通 Benchmark”是正面对上的：多轮的独有分数来自信息获取和状态演化过程，而不是把最终金融 Rubric 重复打四遍。

第五层：MemoryAgentBench 提醒我们，多轮还不只有“用户继续说话”，它还要求旧信息被正确写入、检索、整合和覆盖

MemoryAgentBench 的创新不是再做一个长上下文 QA，而是认为 memory agent 的输入不是一本静态长书，而是随着 interaction 逐步积累的信息流，因此把已有长上下文数据拆成 incremental multi-turn chunks，并分别测试四类能力：Accurate Retrieval 看需要时能不能取回过去的正确信息；Test-Time Learning 看在部署过程中学到的新规则/行为能不能后面继续用；Long-Range Understanding 看分散在很长历史里的信息能不能被整合；Selective Forgetting / Conflict Resolution 看新事实到来以后是否能覆盖旧事实、同时不把仍有效的信息一起删掉。它对你的价值不在于“做 Memory 模块”，而在于告诉你状态保持本身也应该拆成不同 failure mechanism：记不住、找不到、不会整合、该更新时还抱着旧值，这四种错误不能只用一个 final artifact 分数混掉。

第六层：所以 Fixed Multi-turn 的 Rubric 可以从 MemoryAgentBench 借一个很硬的四分法——Carry、Retrieve、Update、Forget

比如金融 R1 已经确认 debt=100，R2 新材料只更新 revenue，R3 又出现 debt restatement=120。真正的多轮评分不能只看 R4 final debt 是否 120，而要区分：R2 时模型是否 Carry 住 debt=100；需要用 R1 covenant 时能否 Retrieve 正确历史；R3 到来后是否 Update 到 120；更新 debt 时有没有错误地把仍然有效的 revenue assumption 一起抹掉，也就是 Selective Forget / Invariant Protection。这样 Rubric 的对象从“最后一个数字”变成了跨轮 state transition。它与普通静态金融 Rubric 的差别就非常清楚：静态 Rubric 判断一个 state 对不对，多轮 Rubric 判断这个 state 是不是在正确时间、根据正确新证据、只改变该改变的部分演化出来的。

第七层：截图里的 Memory Benchmark 综述本身不是一篇新 Benchmark，但它指向一个更重要的趋势——memory evaluation 正从“记得住吗”转向“记忆有没有改变后续行动”

早期 memory benchmark 大量集中在对话 recall：问模型“你几小时前说过什么”“用户喜欢什么”，这能测检索，却未必能证明 memory 对 Agent 工作有用；后来的 FindingDory、ALFWorld/ScienceWorld、Evo-Memory 等越来越把 memory 放进任务决策里。最值得继续看的其实是 2026 年的 MemoryArena：它专门批评“记忆测试”和“行动测试”被拆开，改成 multi-session Memory–Agent–Environment loop，让前一个 session 的动作、反馈和经验成为后一个 session 完成任务的必要条件。实验里一些在静态长上下文记忆 Benchmark 上已经接近饱和的系统，到了真正 interdependent agentic tasks 里依然很差。这给我们的启发是：不要因为 Agent 能复述 R1 的数字就说它有跨轮记忆，只有当 R3/R4 的行动真的依赖并正确使用 R1/R2 经验时，才算测到 agentic memory。

第八层：把四篇放在一起，多轮其实至少有四种完全不同的“因果来源”，以后搜论文也应该沿这四条线搜

第一类是 Temporal Information Fragmentation：同一个完整任务的信息被分散到不同轮次，LLMs Get Lost 就是在隔离这个变量；第二类是 Hidden Intent / Progressive Specification：完成任务需要的要求没有明说，Agent 必须自己恢复或澄清，π-Bench 属于这里；第三类是 State & Memory Evolution：过去状态必须被保留、新信息必须正确覆盖旧状态，MemoryAgentBench 属于这里；第四类是 Experience-to-Action Dependency：前面的经验不是为了以后回答一道记忆题，而是必须真正改变后续行动，MemoryArena 属于这里。以后检索不应该只搜 multi-turn benchmark，而应该分别搜这些机制：`underspecified multi-turn matched control`、`hidden intent proactive agent benchmark`、`incremental multi-turn memory conflict resolution`、`interdependent multi-session agentic tasks`。这样出来的论文会比泛搜“多轮”贴得多。

第九层：这组工作真正逼出来的 Multi-turn Rubric，不应该是一张表，而应该是四层证据

第一层仍然是 Outcome：最终业务目标和 artifact 正不正确；第二层是 Transition：每一轮 `state_before + new evidence/action → state_after` 是否符合 expected delta，同时 invariants 有没有保护；第三层是 Interaction：必要 intent 有没有主动恢复、是否应该问却没问、是否 premature action、用户纠正负担和 turns-to-recover；第四层是 Memory/Dependency：旧信息是否在真正需要时被正确取回、新事实是否替换旧事实、跨 session 决策有没有真正利用过去经验。只有这四层同时存在，我们才可以说“最终做对”和“多轮做得好”是两个可分离的测量对象；否则模型最后交付物对了，你仍然不知道它是不是一路猜对、被用户喂答案、或者恰好最后重算了一遍。

第十层：对当前金融 Benchmark 最值得直接落地的，不是再造题，而是把同一套 World 做成 matched protocol + causal multi-turn rubric

最小改法其实很明确：保持 World Truth、Golden、业务机制和最终任务不变，先做 Full-Information、Fixed Multi-turn、Hidden-Intent Adaptive 三个版本；然后给每一个 Rubric criterion 标一个 multi-turn dependency，例如 `NONE / PRIOR_STATE / NEW_EVENT / CORRECTION / CROSS_ROUND_PROPAGATION / CROSS_SESSION_MEMORY`。`NONE` 只算普通金融 correctness，不拿来证明多轮；真正多轮项必须能被一个反事实实验击中，例如把未来信息提前、删掉中间 event、交换 event 顺序、污染上一轮状态、让 UserSim 不纠正——如果评分完全不变，那这条 criterion 就没有真正依赖多轮。最后再分别报告 Outcome Score、State Transition Score、Interaction Score、Memory/Dependency Score，而不是把所有东西揉成一个总分。这样老师再问“你怎么证明这是多轮”，答案就不再是“因为有四轮”，而是：同一个任务在信息协议改变后出现可测的性能差，而且 Rubric 明确检查只可能跨轮发生的状态更新、纠偏和历史依赖。

一句话背下来：真正的多轮 Benchmark 不是把一份完整任务切成几段，而是把“信息什么时候出现、用户什么时候补需求、旧状态什么时候该保留或更新、过去经验什么时候必须影响后续行动”做成任务本身的因果结构，再用 Outcome、Transition、Interaction、Memory 四层 Rubric 分别证明这些能力真的被测到了。
