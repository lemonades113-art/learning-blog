AWS Skill Evaluation：Skill 真正开始从 Markdown 变成软件工程对象

先给总判断：这篇真正重要的地方，不是 AWS 又给 Agent Skills 加了几个 evaluator，而是它第一次把一个长期被当成“提示词资产”的 Skill，拆成了可以分别测试的运行时行为：该不该选、有没有加载、加载后有没有按步骤执行、出了问题到底该改路由还是改 Skill、改完以后会不会回归、最后能不能把退化直接挡在发布流水线之外。换句话说，Skill 开始拥有和代码类似的生命周期：可观测、可测量、可诊断、可回归、可发布门控、可生产监控。

AWS 原文：Evaluate skill-equipped agents with Strands Evals and Amazon Bedrock AgentCore（2026-09-22）。AgentCore Evaluation 文档：Amazon Bedrock AgentCore Evaluations。

第一层：Skill 一多以后，问题先从“怎么写”变成“系统到底选了谁”

单独只有一份 Skill 时，我们很容易把失败归因成“SKILL.md 写得不够好”；但当系统里有几十、几百份 Skill，Agent 在执行任务之前其实先要完成一个隐藏任务：从一个 catalog 里判断当前请求应该加载哪一份。于是 Skill 系统天然出现了一层 routing problem。一个任务失败，可能是本来应该调用 Skill 却完全没调用，也可能是加载了一个名字相似但不适用的 Skill，还可能是同时需要多个 Skill 却只选了其中一个。AWS 这次最重要的第一步，就是把“最终答案错了”继续往前拆，明确把Skill routing本身当成独立评测对象。这个变化很关键，因为如果 routing 本身不稳定，你继续优化 Skill 正文没有意义；反过来，如果路由一直是对的，问题就应该往执行层找，而不是继续改 description。

第二层：为什么最终答案不能证明 Skill 被正确使用——因为“答对”与“过程合规”是两回事

Skill 的价值通常不只是给模型补一条知识，而是编码一个业务流程，例如先查余额、再查政策、再判断资格、最后提交；因此一个 Agent 即使最后给出了一个看起来正确的答案，也可能中间跳过了必须执行的步骤。对于开放任务，这种“结果看起来对、过程其实违约”的情况尤其危险，因为传统 end-to-end judge 只看最终输出，很可能根本发现不了。AWS 因此把评价对象从 Input → Final Answer 往前扩成 Input → Skill Selection → Skill Load → Prescribed Steps → Final Answer。这不是简单多加一个过程分，而是在改变评测的构造：最终结果只能告诉你“事情做成没”，Skill-level evaluation 才告诉你“系统是否按照被设计出来的能力边界和流程做成”。对于合规、审批、文档处理、工程流程这类任务，这两者必须同时成立。

第三层：三个 evaluator 分别对应三个完全不同的 failure mechanism

AWS 把问题拆成了三个层次。Skill Invoked 是 Strands Evals 里的确定性检查，不调用 Judge，只看一个已知名字的 Skill 是否真的被加载；它最适合做 regression assertion，例如“这个测试输入必须加载 pdf-table-extraction”。Skill Selection Accuracy 则判断某个已经被调用的 Skill 对当前任务来说是不是合理选择，输出 Yes/No；它是在评 routing decision。Skill Instruction Following 完全换了问题：给定已经加载的 SKILL.md，它逐步检查 prescribed steps 在 trajectory 中是 fully covered、mostly、partially、minimally 还是 not followed，并给 1.0、0.75、0.5、0.25、0 五档结果。把这三个放在一起，你就能把“没调用”“调用错了”“调用对了但没照做”拆开，而这三种 failure 的修法完全不同。真正的工程价值就在这里：评测结果第一次直接指向不同的可修改对象。

第四层：Skill Evaluation 真正的价值不是打分，而是让失败能被归因到“该改哪里”

如果一个 case 的 SkillInvoked=0，那么优先检查的是 discovery、catalog exposure、routing prompt 或 skill name/description；如果 Skill 已经被调用，但 Selection Accuracy=0，那么问题多半是 skill descriptions 重叠、catalog 设计不清楚，或者任务边界没有被描述好；如果 Selection=1 但 Instruction Following 很低，说明路由已经正确，真正的问题可能是 Skill 步骤本身写得太模糊、分支太多、顺序不清，或者模型执行能力不够。AWS 官方也明确强调 selection failure 和 instruction-following failure 应该分开解释，因为它们对应不同修复方向。这里最值得学的不是三个名字，而是一条评测原则：一个指标如果不能把失败归到可以修改的技术对象上，它对迭代的价值就很有限。真正成熟的 evaluator 不只是说“这次 0.63 分”，而是能回答“下一次应该改 Router、Skill、Agent Model，还是 Trace Extraction”。

第五层：为什么这件事必须建立在 Trace 上——因为没有 provenance，你根本证明不了 Skill 在运行时发生了什么

Skill-level evaluation 能成立的前提，是系统必须保存足够完整的运行轨迹。AgentCore 把执行记录组织成 session、trace、span，skill invocation 会落到具体 tool-call span；系统可以通过 native skill-loading tool，也可以通过直接读取 SKILL.md 文件识别一次 Skill invocation。这样每个评测结果就不再是脱离运行过程的一个分数，而可以落回具体 sessionId、traceId、spanId，同时 evaluator 还能拿到 invoked_skill、skill_content、available_skills、user_message 和完整 context。于是 Skill 真正形成了一条 provenance chain：用户说了什么 → 当时有哪些 Skill 可选 → Agent 选了哪个 → 实际加载的 SKILL.md 内容是什么 → 后面做了哪些动作 → 哪些步骤有 evidence → 哪些步骤 skipped → 最终结果如何。所谓“Agent 使用了 Skill”从一句推测，第一次变成了可以回放和审计的运行时事实。

第六层：Instruction Following 不是简单逐条打勾，它要求先搞清“这次实际走的是哪条路径”

这一层很容易被忽略。一个真实 Skill 里往往有条件分支：如果条件 A 成立走 1→2→3，如果条件 B 成立走 1→4→5。若 evaluator 机械地要求所有步骤都出现，就会把没有走到的合法分支误判成 skipped。AWS 的 best practice 明确提醒，只应该评价本次运行实际应执行的路径，否则 untaken branches 会悄悄污染 pass rate。这说明 Skill evaluation 本质上并不是“Markdown checklist matching”，而是在做一个更接近条件化过程验证的问题：先从用户请求和运行 context 判断本次应该触发哪条 procedure path，再检查这条 path 的关键步骤有没有 evidence。也因此，一个 Skill 如果同时塞了六个彼此无关的功能，会很难定义统一的正确行为；Skill 的可评测性反过来会约束 Skill 本身的设计粒度。

第七层：真正的工程跃迁发生在 CI/CD——Skill regression 可以像单元测试一样挡住发布

如果这些 evaluator 只是跑完以后给一个 dashboard，意义仍然有限；这次最值得注意的是 AWS 明确把它放进开发和发布流程。Strands Evals 可以在开发期针对固定 case 重跑 Agent，用 SkillInvoked 做确定性 routing assertion，用 judge-based evaluator 检查 selection 和 instruction following，并直接通过 report.test_passes 决定 build 是否失败；AWS 明确提出 Skill quality regression 应该像 failing unit test 一样阻止 release。生产环境则通过 AgentCore Evaluations 直接读取 OpenTelemetry traces，支持单 session 的 on-demand evaluation、历史 session 的 batch evaluation 和线上流量的 continuous sampling。这样 Skill 就真正拥有了版本回归：改了一份 SKILL.md 或新增了一个 Skill，不只是看几个 demo，而是重新跑 catalog routing、执行完整性和关键边界 case；任何明显退化都可以卡在部署门前。

第八层：AWS 这套东西解决的是 Skill 生命周期的“中间层”，不是整个 Agent Evaluation

这里必须把 claim 收紧。Skill Selection Accuracy 和 Skill Instruction Following 都属于 LLM-as-a-Judge，它们本身也需要 calibration，并不是天然真值；AWS 也明确提示不同 evaluation surface 的 threshold 不一定能直接迁移，正式使用前还要验证 trace extraction 是否正确。更重要的是，Skill 被正确选择并且 100% 按步骤执行，不等于最终任务一定成功：Skill 自己可能写错，Tool/Environment 可能返回错误数据，最终业务结果也可能失败。所以 Skill-level evaluation 不能取代 end-to-end task evaluation，而应该嵌在完整链里：该不该调用 Skill → 是否调用正确 → 是否按 Skill 执行 → Tool/Environment 是否正常 → 最终任务是否成功。AWS 这次真正补上的，是以前长期缺失的中间两层：把“能力模块被怎样使用”变成可观测、可测试、可诊断的对象。

再往上抽一层：它实际上是在定义 Skill 的软件工程生命周期

如果完全去掉 AWS 的产品名，这篇可以被压成一条非常通用的工程链：Design → Discover/Route → Load → Execute → Trace → Evaluate → Diagnose → Regression → Release Gate → Production Monitor。Design 阶段定义 Skill 的边界和步骤；Route 阶段决定当前任务是否该选它；Load 阶段确认真的读取了它；Execute 阶段检查实际路径里的关键步骤；Trace 负责留下证据；Evaluate 和 Diagnose 把失败归到路由或执行；Regression 检查 Skill 或 catalog 变化有没有破坏旧能力；Release Gate 让关键退化阻止上线；Production Monitor 则继续发现 catalog drift、真实用户新表达以及长 session 中 instruction following 逐渐变差。Skill 从此不再只是一个文件，而是一个有生命周期、有状态、有质量门槛的工程对象。

对我们自己的 Skill 最直接的启发：以后不只是“写规范”，而是可以真的测它有没有被执行

比如我们现在的论文调研 Skill 规定：先找原问题，再讲具体方法，再交代数据、Reference/GT/Verifier、matched control、实验结果、Blind Spot、Scenario Applicability 和 Project Entry。过去一篇分析最后看起来很完整，但如果中间漏掉 GT、没有讲 matched control，通常只能靠人肉阅读后说“感觉还有 gap”。照 AWS 这套思路，可以把这份写作 Skill 直接变成 testable object：先确认这类请求是否选择了正确 Skill；再从最终分析轨迹里逐项检查“原问题有没有 evidence、Concrete Method 是否讲到可复现、数据和 verifier 是否出现、有没有区分论文证明了什么和没证明什么、有没有落到项目入口”；如果某项缺失，就直接标成 skipped，并进入 regression case。这样 Skill 才从“规范文档”升级成“可以持续验证执行质量的系统”。

一句话复述

AWS 这篇真正做的，不是给 Skill 再加三个分数，而是把 Skill 从“模型可能参考的一份 Markdown”升级成“运行时可观测、选择可评测、步骤可验证、失败可归因、版本可回归、退化能阻止发布的软件工程对象”；它最重要的意义，是 Skill 第一次开始拥有自己的 Evaluation Lifecycle。

论文 / 技术调研默认：原问题 → 具体机制 → 数据与 Trace → Measurement → Failure Attribution → Claim Boundary → Project Entry；最终结论必须说明“它到底把哪个工程对象变得可测了”。
