研究问题驱动的专业 Agent Benchmark 构造

我觉得这部分应该写成论文里的一个研究设计逻辑，核心是回答：

为什么不同 Benchmark 采用不同的题目合成方式？我们应该如何为 CFO-WorkBench 选择合适的构造方法？

这里不能写成“我们把 Data World、WorkFactory、FinancialAuditBench 的方法整合起来”，因为这会让人觉得我们只是堆砌已有技术。

我建议把核心观点写成：

专业 Agent Benchmark 的构造不存在统一的技术路径。不同研究根据其希望测量的能力、任务单位和评价目标，选择不同的任务构造机制。因此，Benchmark 的设计应从研究问题出发，确定必要的任务要素，再选择能够支持目标测量的构造方法，而非预先要求所有系统具备相同的生成组件。

这句话可以成为这一节的中心论点。

一、先确定论文应该怎么讲

我建议分成三个层次，千万不要一上来就写 DAG、Oracle、Kernel、Rubric。

第一层：研究为什么需要这类 Benchmark。

企业专业工作很复杂，模型在知识问答、单步计算上的成绩，无法充分说明它能否完成实际工作。Benchmark 要把专业能力变成可执行任务，并通过专业交付物评价模型。

第二层：已有研究是怎么构造任务的。

  • Data World：从业务世界生成机制出发。
  • FinancialAuditBench：从真实审计统计和专业知识出发。
  • WorkFactory：从专业工作意图出发。
  • APEX-Accounting：从专家编写的会计工作任务出发。
  • DeliverBench：从真实项目和多阶段交付出发。

这些方法对应不同的研究目标、任务单位和评价对象。

第三层：我们为什么选择自己的方法。

根据 CFO-WorkBench 想测量的能力，确定需要哪些业务材料、专业规则、参考标准和评分机制，再选择适当的生成和验证组件。

这里的核心概念，我建议叫：

Research-question-driven Task Construction

研究问题驱动的任务构造

根据目标测量能力，选择最小充分的任务生产与验证机制。

二、论文中可以直接这样写

下面这版可以作为论文 Methodology 前面的研究设计论述，也可以作为 Related Work 最后一节的过渡。

论文正文草稿

2.X 研究问题驱动的专业 Agent Benchmark 构造

1. 从专业能力测量到任务构造

专业 Agent Benchmark 的核心目标，是评估模型在特定专业工作环境中完成实际工作的能力。与传统知识问答和单步计算任务相比，专业工作通常涉及多源信息获取、业务规则应用、专业判断以及结构化交付。因此，Benchmark 需要将目标专业能力转化为可执行的工作任务，并通过可观察的交付结果和专业评价标准衡量模型表现。

这一目标带来了一个重要的构造问题：如何将复杂的专业工作转化为具有业务真实性、信息充分性和可评价性的 Agent 任务？

2. 现有研究采用了不同的任务构造路径

近期专业 Agent Benchmark 与任务合成研究呈现出多种不同的构造方式。

Data World 从业务世界的生成机制出发，先定义变量之间的关系并构建底层真实状态，再将其投影为具有现实数据特征的文件，进而生成分析任务和评价标准。其设计重点在于解决开放式数据分析任务中的真值可追溯与结果可验证问题（Li et al., 2026）。

FinancialAuditBench 从真实审计业务统计和专业知识出发，利用差分隐私聚合统计、财务计算关系及审计专家参与，构建合成企业审计项目和工作底稿。其重点在于解决真实审计数据难以公开获取的限制，同时保留专业审计任务的真实性和可评价性（Huang et al., 2026）。

WorkFactory 从专业工作意图出发，通过信息支持图识别完成目标交付所需的信息及其来源，再利用执行探测和任务修复提高生成环境的可执行性，最终收集教师模型的执行轨迹。其重点在于规模化生产能够支持可靠专家监督的专业训练任务（Zeng et al., 2026）。

APEX-Accounting 采用专家主导的任务构造方式，由会计专业人员在模拟企业环境中设计并完成任务，同时制定相应评分标准，以直接评估模型完成日常会计工作的能力（Benchek et al., 2026）。

DeliverBench 则以真实专业项目为起点，由领域专家还原项目工作流程，将多个子任务及其交付依赖连接起来，并通过后续材料和客户反馈考察 Agent 的持续交付能力（Liu et al., 2026）。

这些研究表明，专业 Agent 任务可以从业务世界、专业工作意图、领域专家和真实项目等不同起点构造。其差异反映了研究目标、任务单位、输入环境和评价对象的不同，并不要求所有 Benchmark 采用完全相同的生成架构。

3. 任务构造的共同要求与可选机制

尽管具体生产路径不同，一个可用于专业能力测量的 Benchmark 仍需要回答几个共同问题：

  1. 目标能力是否明确： 任务实际测量什么专业能力，任务设计是否能够体现该能力？
  2. 输入是否充分： Agent 能否从提供的业务材料和工具环境中获得完成任务所需的信息？
  3. 结果是否可验证： 是否存在可信的参考结果、专业规则或可接受答案范围？
  4. 评分是否有效： 评价标准能否反映专业工作的正确性、证据支持和交付质量？
  5. 任务是否经过验证： 是否通过独立执行、专业审核和实际模型测试，检查任务的可解性、真实性及区分能力？

在此基础上，世界生成器、信息依赖图、计算依赖图、专家出题、教师轨迹、多阶段状态机等均可作为任务构造的可选机制。是否采用某一机制，应由目标任务的实际要求决定。

例如，研究跨文件证据核查，需要保证不同材料之间存在可追溯的事实关系；研究多阶段项目交付，需要保留前序产物及其后续依赖；研究确定性财务计算，则可以通过可复算的业务内核和独立边界测试建立参考标准。

因此，Benchmark 构造更适合采用研究问题驱动的模块化设计：首先确定目标能力和任务单位，再选择满足任务真实性、可解性和可评价性要求的必要构造机制，并通过独立验证确认其有效性。

4. 对 CFO-WorkBench 的设计启示

对于企业财务 Agent，研究重点应落在具体的企业专业工作机制及其测量缺口上。不同 CFO 工作任务具有不同的信息结构和决策要求，因此应根据具体任务选择构造方式。

例如，集团内部资金往来核查需要关联不同法律实体的账簿、合同和银行流水，重点在于多源证据的关联及专业核对；目标导向的证据搜寻任务需要控制委托目标与可用证据之间的关系，重点在于观察目标变化是否影响 Agent 的证据搜索和使用行为；完整 CFO 项目交付则需要记录阶段依赖、文件版本和外部反馈，重点在于评价跨阶段交付的一致性。

因此，CFO-WorkBench 应以目标专业能力为依据，为不同任务族配置相应的材料生成、参考结果、评分和验证机制，并共享必要的生产与质量控制基础设施。

最终，研究贡献应建立在对特定企业专业能力测量缺口的识别，以及对相应任务设计有效性的实证验证之上，而非仅以生成组件的数量或系统架构的复杂程度作为依据。

四、结合你刚上传的 CFO 链路包，应该怎么落地？

我看了一下你们现有的 CFO 生产链，这里有一个很好的例子。

你们已经有一条比较复杂的 CFO 任务生产线。

例如 CFS01：

  • 任务：2025 年度集团资金情况；
  • 输入：89 份文件；
  • 交付：Excel 现金流量表及流水分类底稿、Word CFO 汇报；
  • 任务涉及：集团资金状况、交通银行年度报送、新产线资本开支、对香港公司追加放款；
  • Claims：84 条；
  • Score Spec：173 项评分标准；
  • Source Registry：369 条来源记录；
  • Rule Registry：29 条规则；
  • Gaps：9 项信息缺口记录。

这说明 CFS01 的任务单位已经是一个综合财务工作委托，涉及大量材料、专业规则和多项交付要求。

它的生产质量也有明确的工程化设计。

交付包 README 描述的通用单题流水是：

这里还有一个值得强调的细节：

CFO 生产线采用场景族生成器加共享质检引擎的结构。包内 README 记录了 111 个 CFO 场景族，以及 75 个现有题号的对应生成器。

而且它自己的 DAG 也按任务线区分：

  • 线1：一次性红旗检测任务，DAG 表示定位、取数、复算、交叉核对、量化和判定。
  • 线2：递归多期状态任务，DAG 表示逐期计算及跨期依赖。

这比要求所有 CFO 任务都使用同一种 DAG 更合理。

需要注意，上述是交付包内的任务配置和架构记录，数量及结构不等于本轮已经完成全生产线的独立运行验收。

五、论文究竟应该突出什么贡献？

我建议你特别注意这三句话：

不建议这样写建议这样写
我们融合了五篇论文的任务生成方法我们根据目标专业能力选择任务构造机制
我们设计了一个包含多种 DAG 的复杂系统我们将业务依赖、证据支持和任务执行分别建模，以满足具体任务需求
我们生成了大量复杂财务题我们定义了目标任务单位，并验证其能否测量目标专业能力

还有一个更深的区别：

Benchmark 是测量工具，Task Factory 是生产工具。

Factory 可以有很多模块，但每一道题只需要使用与它的研究目标相关的模块。

Benchmark 最终需要证明的是测量有效性，而不是工厂有多少个文件、多少张 DAG、多少个生成器。

六、我建议最终论文按照这个结构组织

Introduction

  1. 企业专业 Agent 为什么需要新的能力测量？
  2. 现有财务 Agent Benchmark 测量了什么？
  3. 我们发现了什么具体测量缺口？
  4. 我们提出什么任务单位和 Benchmark？

Related Work

  1. 专业 Agent Benchmark 的任务设计；
  2. 合成业务环境与数据生成；
  3. 专业工作流与多阶段交付。

Benchmark Design

  1. Research Question；
  2. Target Capability；
  3. Task Unit；
  4. Task Construction；
  5. Oracle and Rubric；
  6. Quality Assurance。

Experiments

  1. 模型总体表现；
  2. 不同能力维度的表现；
  3. 失败模式；
  4. 专家评分一致性；
  5. 消融实验与有效性分析。

我的建议是：现在先把 Related Work 和 Benchmark Design 之间的逻辑写好，暂时不要急着宣布 CFO-WorkBench 采用哪一种完整生产架构。

因为你们真正要争取的论文贡献，可能来自发现现有财务 Agent Benchmark 没有充分测量的某种企业专业工作机制。那时我们才知道需要补充世界生成、证据关系、多轮状态，还是一种完全不同的任务设计。

另外提醒：刚上传的压缩包中有 README 含疑似有效的外部数据源账号和 Token 明文，建议及时轮换，并在后续共享版本中清理。

下一步我最建议做的是：把 CFO-WorkBench 现有的三个候选 Story 分别代入这套框架，写出每个 Story 的任务单位、必要构造模块、现有 Benchmark 缺口和实验假设。这样我们就能从“怎么建工厂”真正走到“这篇论文研究什么”。
