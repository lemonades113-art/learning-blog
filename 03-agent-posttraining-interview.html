Agent / Post-Training 面试七问：把最容易被追问的地方提前讲完

这组问题表面上很散：Harness、OPD、自进化、幻觉、FFN、工作方向，但其实都在追同一件事：你是否真的知道 Agent 的能力是怎么被造出来、怎么被测出来、失败以后怎么定位，以及什么时候应该改模型、什么时候只改系统。所以回答不能停在名词解释，而要主动把第二层、第三层追问一起封住。

第一问：实现一个 Agent 时，Harness 到底怎么设计？

Harness 不是简单包一层模型调用，它真正负责的是把模型能力变成一个可重复、可归因的实验过程。我会把系统拆成三层：Environment 持有真实世界状态，例如文件、数据库、工具结果和任务进度；Agent 只根据当前合法可见信息决定下一步 action；Harness 位于两者之间，负责轮次调度、工具协议、超时重试、上下文拼接、轨迹记录和 episode 结束条件。这里最重要的原则是 Harness 不能偷偷替 Agent 完成能力，例如自动补模型没给出的参数、把 hidden state 直接变成提示词、工具失败以后替模型选择另一条路线，否则最后分数上升了，却无法判断是 Agent 变强还是 Harness 在代做。真正合格的 Harness 要把“可见输入、允许动作、状态转移、停止条件、评分证据”全部显式化，并保存完整 trajectory，让同一任务换一个模型还能按完全相同的规则重放。

继续追问时要能答：怎么证明 Harness 没污染 benchmark？至少做三类验证：一是 leakage test，故意把 benchmark-private 信息换成错误值，看 Agent 输出是否跟着变化；二是 scaffolding ablation，同一个模型分别跑 bare model、tool-only、retry、完整 Harness，看每一层边际贡献；三是 replay / determinism test，固定任务状态和随机种子后重跑，环境转移和 scorer 要可复现。Harness 和 Environment 的边界也要说死：Environment 决定“世界现在是什么”，Harness 决定“这一轮怎么让 Agent 和世界发生交互”。

第二问：OPD 到底是什么？为什么一定要 On-Policy？

如果这里的 OPD 指 On-Policy Distillation，最核心的问题不是“teacher 教 student”，而是训练分布和真实运行分布是否一致。传统蒸馏更像老师提前生成一批固定答案，student 在这些静态数据上学；但 student 上线以后真正访问的是自己产生的状态，一旦 student 和 teacher 的分布差得很远，就会出现 training distribution 和 inference distribution 不一致：训练 loss 看起来很好，student 自己 rollout 时还是不断掉进原来的错误模式。On-Policy 的改法是让 student 先按当前策略 rollout，再让 teacher 对 student 真正到达的状态提供指导，所以 student 今天是 50 分，就主要在自己 50 分附近真实犯错的位置上学；能力提升到 70 分以后，训练分布也跟着移动。

继续追问时要能答：这和 RL 有什么区别？RL 常给 trajectory-level 或 outcome-level 的 scalar reward，再做 credit assignment；OPD 可以直接让 teacher 对 student 当前 token / trajectory 分布提供更密的监督。它也不是没有代价：每批 student rollout 都需要 teacher inference，成本高；teacher 太强时，student 与 teacher 分布差得太远，反而可能学不动，所以会需要 curriculum、teacher checkpoint staging、KL 约束或局部蒸馏。也就是说，OPD 主要解决 exposure mismatch，但不会自动解决 teacher quality、teacher-student gap 和 optimization stability。

第三问：模型自身能力和 Self-Evolution 到底是什么关系？

这里最容易偷换概念：最终任务分数提高，不等于模型参数里的能力提高。同一个 base model 加 search、reflection、verifier、memory、retry，也可能从 50 分变成 80 分，但这首先说明整个 agent system 更强了，不能直接说 foundation model“进化了”。所以我会把 self-improvement 分成两个 update surface：一类改模型本身，例如 self-training、RL、distillation、weight update；另一类只改 scaffold，例如 prompt、memory、tool、workflow、代码和控制策略。真正判断“谁进化了”，至少要看持久性、泛化性和因果归因：一次 episode 内反思以后做对了，只能叫 adaptation；下一次新 session 没有旧轨迹还能稳定改善，才说明变化被持久化；而且必须在独立 holdout 上仍然成立，否则只是记住旧题。

继续追问时要能答：如果删除新增 memory 后能力消失，变化来自 memory；换回旧模型权重以后仍然存在，说明不是 model learning；只有做过这种 ablation，才知道能力提升到底来自哪里。Self-Evolution 本质上不是一个神秘算法，而是“经验产生 → 失败归因 → 选择该修改哪个 surface → 验证修改 → 决定是否永久保留”。

第四问：Agent 因为知识缺失产生幻觉，怎么解决？

不能只回答“加 RAG”，因为所谓知识幻觉至少有四种不同失败：模型根本没有知识；系统有知识但 retrieval 没召回；已经召回但模型没正确使用；当前根本没有足够证据，但模型仍然选择编一个答案。四种都叫 hallucination，就不知道该修哪里。真正的方案是把 knowledge access 和 answer policy 分开：需要外部事实时，先通过 search、database、RAG 或 tool 取证；生成时让 claim 和 evidence 显式绑定；证据不足时允许澄清、继续检索或 abstain，而不是把“必须回答”当默认动作。

继续追问时要能答：怎么证明真的解决了？Retrieval Recall 看该拿到的证据有没有拿回来；Evidence Precision 看拿回来的是否相关；Unsupported Claim Rate 看最终回答里有多少事实没有证据支持；Citation Correctness 看引用是否真的支持对应 claim；再加 closed-book 对照，关闭 retrieval 后性能掉多少，确认提升真的是外部知识贡献。不要只依赖模型自己报 confidence，因为 verbal confidence 不天然等于校准后的正确概率，更稳的是把“有没有充分证据”做成系统状态。

第五问：Self-Evolution 有哪些经典形式？最大问题是什么？

按“到底改了什么”来分会比背论文名字清楚。最轻的一层是 runtime search / reflection，本轮多试几条轨迹但不留下永久改变；再上一层是 memory / skill / prompt evolution，把经过验证的经验保存下来供未来 episode 使用；再往上是 code / tool / workflow evolution，直接改 agent scaffold；最重的一层才是 model update，把经验编译成训练数据，再通过 SFT、RL 或 distillation 写回参数。真正最大的困难不是 mutation，而是 promotion：系统怎么知道一次看似成功的修改值得成为长期状态。

继续追问时要能答：如果生成 candidate、评价 candidate、决定保留 candidate 的都是同一个模型，很容易 self-confirmation：自己提出一个办法，自己觉得很好，再把它永久保存。错误一旦进入长期 memory、code 或 model weights，后面还会继续生成支持自己的证据。所以更可靠的闭环应该是 Candidate → Shadow/Test → Independent Evaluation → Holdout → Promotion → Rollbackable Deployment。越接近永久修改，验证门槛越高。自进化最难的不是“怎么让系统改自己”，而是“怎么建立一个独立于 proposer 的 judge，证明这个修改在没见过的数据上真的提高目标能力，而且没有破坏别的能力”。

第六问：Transformer 去掉 FFN 可不可行？除了“非线性”和“参数多”还有什么？

先避开一个容易被追问穿的答案：不能说“没有 FFN 后 Transformer 就线性了”，因为 self-attention 里还有 softmax，本身就有非线性。FFN 更重要的作用是 token 内部的 channel transformation。Attention 主要解决“当前 token 应该从哪些 token 获取什么信息”，也就是跨 token 的信息路由；拿到这些信息以后，还需要对当前 hidden representation 做特征重组、放大、抑制和组合，FFN 就承担这一步。标准 FFN 通常先把 d 维表示扩到更高维，再经过 activation / gating，再压回来；现代 SwiGLU 还有乘性 gate，所以它不只是加参数，更是在给每个 token 提供独立的特征计算能力。

继续追问时要能答：Q/K/V 和 output projection 不是也能做 channel mixing 吗？能做一部分，但它们主要服务 token-to-token routing，FFN 则把 token mixing 和 channel mixing 解耦。理论上可以设计 attention-only 或其他 block 替代 FFN，所以不是“数学上不可删”；但直接在标准 Transformer 里把 FFN 拔掉，等于同时砍掉很大的参数容量和 token-wise computation。MoE 为什么通常替换 FFN 而不是 attention，也说明大量可条件选择的知识和计算容量很适合放在 position-wise expert 中。结论不是 FFN 神圣不可删，而是：可以替代，但必须补回 token 内部的 feature transformation、gating 和 capacity。

第七问：你期望的工作方向是什么，怎么避免答成空话？

我不会只说“我想做 Agent / RL / Post-Training”，因为下一句一定会被问“具体想解决什么问题”。更完整的回答是：我希望做复杂 Agent 的 post-training、evaluation 和 self-improvement 闭环，核心问题是模型在长程真实任务里失败以后，怎么判断是 base-model capability 不够、search 没搜到、知识没拿到、工具执行失败，还是 Harness / state management 有问题，然后针对不同根因选择不同优化 surface。如果只是 search 不够，就增加 test-time compute；如果稳定缺能力，就进入 RL / distillation；如果是知识问题，就补 retrieval / memory；如果是系统执行问题，就改 Harness，而不是任何问题最后都归结成“继续训模型”。

继续追问时要能答：具体抓手可以落到三个对象：第一，可执行的 long-horizon benchmark / environment，保证能力真的能被测出来；第二，post-training / on-policy learning，研究模型如何从真实失败轨迹中持续学；第三，controlled self-improvement，研究一次经验在什么证据条件下可以从临时修复升级成长期 memory、skill、code 或 parameter update。这样“方向”不是兴趣标签，而是一条完整问题链：怎么测 → 怎么归因 → 怎么改 → 怎么证明改对了。

最后：真正的防追问结构

每道技术题都至少要做到三层：第一层回答题面；第二层主动回答为什么；第三层提前封住反例和边界。写完以后把答案里的名词、比较级和因果词圈出来——“更稳定”“更强”“解决 mismatch”“需要 promotion gate”“teacher 太强”——每一个都是潜在追问。凡是不能继续回答“为什么、怎么做、怎么算、什么时候不成立”的，都说明这一句还没写完。

默认写法：总判断 → 主问题 → 追问闭环 → 指标 / 边界 / 反例。
