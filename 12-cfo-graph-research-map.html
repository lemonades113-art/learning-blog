CFOGraph：从论文节点图谱找到真正的研究缺口

核心问题：已有论文各自连通了哪些技术节点？哪些关键的跨图连接仍然缺少可验证证据？我们能不能把现有 CFO 工程变成一篇方法和实验都足够强的论文？

建议聚焦一条主链：企业财务事实的因果图 → Agent 必要专业决策依赖图 → 独立证据与评分图 → 模型实测的失败归因。连通图本身属于工程贡献；如果能通过受控干预证明哪些决策关键依赖导致模型失败，以及现有评分遗漏了什么，才有希望形成更强的研究贡献。

一、研究定位：缺少节点，还是缺少可验证的边？

已有工作中，企业财务材料生成、Agent 工作流、DAG 难度控制、自动 Oracle、反事实任务对和评测反馈都有人做过。我们不能把几个已经存在的组件串接起来，就断言“首次构建了这样的闭环”。

研究的价值在于一条边能否改变科学判断。例如，把业务事件与专业决策连接之后，是否可以预测哪些事实改变会跨越付款决策边界？把决策与证据图连接之后，能否发现原 Rubric 未覆盖的关键控制要求？再把这两条映射带入模型实验，能否在控制文件长度和任务规模后稳定解释失败？

因此整条论文叙事从“已有论文的节点覆盖”出发，最终落到“缺失连接的可证实增量”。

五、核心方法：三张 DAG 要各自定义，再建立严格映射

GRAPH 1 · Business Causal Graph

财务业务因果图：企业发生了什么？

节点表示业务事实、单据、状态或决策；边表示业务规则中的依赖或状态传播。

采购合同 / 验收 / 发票
→
应付确认与付款申请
→
审批权限 + 资金可用性
→
是否执行付款
→
银行流水 / 凭证 / 报表

对应 simeco 的逐笔事实与 CFO 跨期状态机。这里的“因果图”是受业务制度与模拟程序约束的机制图，不能将其直接宣称为从真实观测数据中识别出的统计因果关系。

GRAPH 2 · Decision Dependency Graph

专业决策依赖图：Agent 真正必须判断什么？

节点为必要专业判断，边为前置决策条件。

供应商与付款单一致？
审批有效及生效时间正确？
资金是否充足？
是否重复支付？
上述必要判断
→
放行 / 暂缓 / 请求核实
→
正确交付或执行结果

关键在于识别能改变最终结论的节点，而非只统计 DAG 总量。审批缺失可能决定整笔款项必须 HOLD，而格式错误未必改变经济决策。

GRAPH 3 · Evidence & Verification Graph

证据与验证图：凭什么判断 Agent 对或错？

节点为原始证据、验证操作、判据和评分项；边表示证据支持关系。

审批记录 + 权限表 + 时间戳
→
独立业务规则检查
→
Oracle + 关键门禁
→
评分与错误归因

不能只因模型报告写了“已核对审批”就给满分，也不能把一种参考答案的表面格式当作唯一合法解。独立验证器需要接受正确变体并拒绝明确错误解。

决策关键性：怎样把图节点变成可测量变量？

设业务世界为 W，正确决策为 d*(W)。对业务事实 x 实施合法干预，生成 W'。当 d*(W) 与 d*(W') 不同，说明该干预在该业务世界里跨越了一个决策边界。

C(x; W, W') = 1[d*(W) ≠ d*(W')]

这个二值定义是方法起点，不代表完整难度理论。未来可加入违规严重度、货币损失、跨期传播范围和耦合关系。核心研究问题是：决策关键依赖是否比普通 DAG 节点总数更能解释 Agent 的实际失败？

六、跨图需要真正验证的三条边：E1、E2、E3

E1

业务事实 → 必要专业判断

每项关键业务事实必须明确对应到决策图中哪个判断：审批有效性对应付款放行门，资金余额对应现金约束。

E2

专业判断 → 独立验证证据

关键决策节点需映射到具体材料、可执行判据、正确结果和评分依据，避免只看文字叙述。

E3

受控事实干预 → 模型行为变化

改动真实业务世界中的关键事实、重算 Oracle，再检查模型是否响应并定位失败机制。这一项是研究假设的实证部分。

E1 + E2 构成方法；E3 构成研究证据。但这三类机制各有论文先例，必须进一步展示它们在 CFO 财务链路中带来了哪些前人没有充分测量的结果。

七、一个完整的付款预检干预示例

基础场景

付款申请 100 万元；可用资金 120 万元；二级审批缺失；其余必要条件满足。

正确决策：暂缓付款

受控干预

添加一条在决策时点前生效、由有权限人员完成的二级审批，其余关键事实保持不变。

干预后：允许放行

业务图：插入审批事件并更新相关状态，不能只改题面文字。决策图：审批校验由不满足转为满足，综合决策随之变化，其余条件保持不变。证据图：重新生成审批、资金及决策断言，核实模型使用的是正确的审批记录。

可以为每组干预生成一份机器可读的“因果变更凭证”（以下为建议接口，尚未在工程中实现）：

intervention:
  target: approval_level_2
  operation: add_valid_approval
  effective_before_decision: true

expected_delta:
  approval_valid: false -> true
  payment_decision: HOLD -> ELIGIBLE

invariants:
  - payment_amount
  - supplier_identity
  - cash_balance_before_execution

evidence:
  - approval_record_id
  - authority_policy_id
  - approval_timestamp

verification:
  - approval_rule_check
  - payment_decision_check
  - invariant_preservation_check

系统需要检查目标事实已变化、所有应变状态正确传播、其他不该变的业务事实保持不变。随后对同一个模型运行基础题和干预题；如果它没有按照新审批改变决定，再从交付物与轨迹分析是证据检索、状态更新、规则适用还是决策传播的问题。

归因边界：观察到的轨迹只能支持行为层面的失败归因，不能直接证明模型内部真正如何思考。因果结论需要受控实验、独立真值与多次复现，不能单靠模型自己的解释文本。

八、什么样的结果才真的算 strong？

研究层次做到了什么判断
Level A · 工程集成simeco 接 CFO 状态机，自动生成任务、Golden、Rubric工程价值高，独立方法新颖性偏弱
Level B · 图耦合方法业务图—决策图—证据图对齐，支持干预、重算与配对评分具备方法贡献潜力
Level C · 能力机制发现验证哪些图结构预测模型失败、能否跨企业和任务泛化、能否发现评分盲区最有希望成为强论文

Anchor、TASTE 和 CausalPrism 等工作已经研究参数化任务难度、迭代反馈和因果能力拆解，所以 Level C 不能停留于“某个新指标与错误率正相关”。需要严格的匹配对照与泛化证据。

  1. 匹配对照：使输入长度、文件数量、预算尽量接近，区分重复结构增加和关键决策依赖增加。
  2. 受控干预：明确哪个合法业务事实导致正确结论变化，保持其他关键变量不变。
  3. 独立验证：使用生成器之外的财务复算器重算，抽样交给专业人员核验。
  4. 多模型实证：固定工具、预算和场景，多模型重复运行，报告关键错误率、评分分歧与不确定性。
  5. 泛化测试：在未参与开发的企业、规则组合和其他任务族上验证同一机制。

单独在 R16 付款预检调出来的指标，可能只是场景特定的拟合。若能在 R6 月末关账、R9 税务或其他业务任务族中仍有预测价值，研究强度就会提高。

九、还有一个可能更强的问题：评分器到底漏测了什么？

业务要求：必须检查二级审批
→
决策图：审批是必要条件
→
评分图：缺少审批有效性检查
→
绕过审批也可能高分

如果决策图中的关键节点找不到对应 Verifier，就构成测量盲区；反过来，如果评分器要求不必要的表面格式，也可能误判正确的业务解。

因此可以提出一类跨图一致性审计：检查专业决策依赖是否有可执行评分证据、每个高权重判据是否有真实业务依据、关键业务门是否具有足够的失败约束。

已有样题记录的 gating_count=0 为这一问题提供了直接动机。真正有分量的实验应证明：图对齐审计找出了旧 Rubric 的真实漏测项，而这些项确实会改变模型的业务成功判定，并通过专家复核。

十、论文贡献应该怎样写？

推荐暂拟标题：

CFOGraph: Causally Grounded and Verifiable Evaluation of Enterprise Financial Agents

Contribution 1：Graph-grounded financial task construction

通过可追溯的财务机制图，结合业务单据、账务状态和跨期规则，生成具有真实业务依赖的任务。它是后续研究的可信基础。

Contribution 2：Decision-critical intervention and verification

建立业务图—决策图—证据图映射，支持关键事实干预、无关扰动、证据缺失测试以及独立 Oracle 与不变量检查。这是最值得打磨的核心方法。

Contribution 3：Empirical validity and capability attribution

跨模型、跨企业和跨任务族，检验决策关键依赖相对传统结构指标的解释力，定位现有评分中的关键盲区。这一项将决定整篇论文的科学价值。

没有第三项，就很容易变成结构合理的 Benchmark 工程介绍。研究发现不应该提前写死，需要由实验的支持或反证来确定。

十一、最小执行路线：先恢复一题，再扩第二个场景

第一步不是扩展到更多 CFO 题目，而是对 R16 付款预检建立一份从业务事实、关键判断到评分证据的完整映射。

1

恢复业务图。 列出付款事件、单据、审批、资金、状态和业务约束，确定真实依赖。

2

恢复决策图。 找出真正影响放行、暂缓、核实的判断和关键路径，识别纯模板重复节点。

3

恢复证据图。 将每个关键决策映射到现有 Golden、Rubric、Verifier 和证据文件，标明已验证、仅声明、缺失。

4

构造一组合法干预。 改动审批事实，重算关联状态、Oracle 和关键门禁，检查所有应保持的不变量。

5

真实模型运行。 做基础题/干预题配对，在相同预算下多次运行，记录实际决策变化、执行证据与失败归因。

6

跨场景验证。 在 R6 月末关账中使用相同映射和干预协议，评估可复用性与研究增量。

输出对象验收要看到什么
业务图有业务含义的节点、状态、规则和真实依赖
决策图必要判断、关键条件、可能改变最终决定的节点
证据图每一关键判断的来源证据、Oracle 与评分检查
跨图映射已实现 / 仅声明 / 尚缺失的具体连接
干预实验改变的事实、影响的结果、正确性与不变量证明
Agent 实测原题—变体配对表现、失败位置、不同模型差异

十二、给老师的口述版

我最近把 CFO 相关的论文重新按技术链路梳理了一遍，发现已经有很多工作分别解决了真实金融任务、任务与验证器自动生成、图结构难度、反事实任务和模型评分问题，甚至一些连接已经做得非常完整，比如 Anchor、FinalityBench 和 TASTE。

但从我们自己的 CFO 工厂来看，有一个值得进一步研究的点：我们已经有企业财务数据、跨期状态机和推理 DAG，但是 DAG 的结构复杂度、真正影响业务决策的专业依赖，以及评分能够验证的能力之间，还没有建立充分可靠的对应。

所以我想从三张图切入。第一张是业务事实因果图，记录交易、单据、账簿和状态怎样变化；第二张是专业决策依赖图，表示完成任务到底必须判断哪些业务条件；第三张是证据验证图，表示每个关键判断由什么材料和评分规则验证。

方法上，让三张图保持一致，然后围绕真正影响决策的节点生成受控变体。比如增加无关材料时正确决策应该不变，修改有效审批时正确决策应该变化，关键证据缺失时 Agent 应该暂缓或核实。

最重要的实验是证明：相比增加文件数、DAG 节点数和执行长度，这些决策关键依赖能不能更好地解释模型为什么失败；同时还能发现原有 Rubric 漏测的业务风险。

如果这条链能在付款预检、月末关账等不同场景上得到验证，我们的贡献就可以从自动产题，提升到一种面向真实企业工作流的可控能力评测方法。

最终研究押注：业务因果图 → 决策关键依赖图 → 独立证据评分图 → 模型实测失败归因。
分水岭：是否能用可复现的独立实验，证明这种跨图映射识别出旧 Benchmark 测不准的专业能力，并在其他 CFO 场景中复用。
